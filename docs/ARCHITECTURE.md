# Architecture

## The constraint that shapes everything

Beeper is Matrix under the hood with end-to-end encryption: **only a device logged into your account can decrypt your messages**. Beeper therefore has no third-party cloud API. The official surface is the **Beeper Client API** — an HTTP + MCP server embedded in a logged-in Beeper client, historically Beeper Desktop (`localhost:23373`) and now also the official headless **Beeper Server** (`beeper setup --server --install`, same API, same port, no GUI).

Consequence: Claude Messenger is a *client* of a Beeper endpoint that must run somewhere logged into your account. Where that endpoint runs is pure configuration (`BEEPER_BASE_URL`); nothing else changes.

> In practice we run **Beeper Desktop** for that endpoint, including on headless hosts (under Xvfb). The headless **Beeper Server** is deliberately unused: [beeper/cli#21](https://github.com/beeper/cli/issues/21) is open and unanswered, and reports it deleting a legacy account's bridge connections across every device. Because the endpoint is pure configuration, this choice touches nothing above `providers/` — which is the property this seam exists to provide.

## Layers

```
Claude (Claude Code / Desktop / claude.ai)
   │  MCP (stdio locally, or Streamable HTTP + bearer token when hosted)
┌──▼──────────────────────────────┐
│ mcp/    curated tools           │   deliberately narrow: no delete/archive
│ assistant/ automations          │   the daily digest (writes with the model);
│                                 │   @Claude mentions (own messages only)
├─────────────────────────────────┤
│ policy/ GuardedMessenger        │   PolicyEngine (pure decisions)
│         + JSONL audit log       │   read filters, send gates, rate limits
│         GuardedAccessRequester  │   keeps only credentials it can keep
├─────────────────────────────────┤
│ core/   Messenger port          │   provider-agnostic domain models
│         AccessRequester port    │   how the credential comes to exist
│         LanguageModel port      │   text in, text out: no tools
├─────────────────────────────────┤
│ providers/beeper/               │   @beeper/desktop-api adapter
│ providers/claude-code/          │   `claude -p` on the owner's subscription,
│                                 │   which talks to Anthropic, not Beeper
└──┬──────────────────────────────┘
   │  HTTPS + bearer token
Beeper Client API (Desktop app OR headless Beeper Server)
   │
Beeper cloud bridges ⇄ WhatsApp / Signal / Telegram / iMessage / ...
```

### Rules that keep it clean

1. **Nothing above `providers/` imports a provider SDK.** The `Messenger` interface (`core/messenger.ts`) is the seam. Tests run against `FakeMessenger`; a raw-Matrix provider (via Beeper's own `@beeper/pickle` / `@beeper/chat-adapter-matrix`) can be added without touching policy, MCP, or CLI.
2. **The tool layer only ever sees the `GuardedMessenger`.** Policy checks happen in-process *before* any provider call; denials throw `PolicyDeniedError` naming the rule. Read results are filtered so denylisted chats never enter Claude's context. Likewise `connect` only gets the `GuardedAccessRequester`.
3. **`PolicyEngine` owns decisions, not I/O.** The clock and the rate-limit store (`RateWindow`) are injected: tests control time with a memory window, while the composition root wires a file-backed window so send limits survive process restarts (each CLI `send` is a fresh process).
4. **Audit content policy**: outbound text is recorded (you must be able to review what was said as you); read message content is never written to the audit log (your history doesn't belong in log files). A watch records which message it handed on (chat and message IDs), never what it said.

## Deployment topologies

| Topology | BEEPER_BASE_URL | Use case |
|---|---|---|
| Local | `http://localhost:23373` | Claude Code/Desktop on the same machine as Beeper Desktop |
| Tunnel | `https://<tunnel-host>` | Remote Claude (web sessions, automations) reaching your desktop via Tailscale/cloudflared |
| Headless server | `http://<vps>:23373` (behind tunnel/VPN) | 24/7 always-on: official Beeper Server on a small VPS (beta as of mid-2026) |
| Always-on desktop | `https://<tunnel-host>` | 24/7 GA fallback: Beeper Desktop + Remote Access on a machine that stays awake |

Beeper Desktop's *Remote Access* setting (Settings → Integrations → Advanced) binds the API to all interfaces and is designed for tunnels; auth stays bearer-token. Beeper ships no TLS — never expose the port raw.

## Extension points (deliberate, not speculative)

- **Streaming/triggers**: `Messenger.watchMessages` delivers messages as they reach the backend, each once, after a `since` time. It landed with its first consumer (the @Claude listener, `assistant/mentions.ts` and `claude-messenger mentions`), its Beeper implementation and its guarded wrapper in one change, as planned:
  - **Guarded**: `GuardedMessenger.watchMessages` checks the read policy before the provider is asked, hands on only the user's own messages whatever the provider returns, filters every message through the same visibility predicate as reads, and audits like a mutation: intent first (mandatory), a delivery entry before each message is handed on (mandatory; IDs only), the outcome last (best-effort). Idle polls write nothing.
  - **Beeper**: the Client API's WebSocket (`/v1/ws`, `message.upserted`) is experimental, so the provider polls message search instead (`providers/watch-by-polling.ts`, every `BEEPER_POLL_INTERVAL_MS`, default 5 s). Each scan re-reads a 10-minute window behind the previous one, because a message can reach Beeper after its own timestamp (a bridge reconnecting); one that arrives later than that is missed. The window follows the host clock, not message timestamps, so a message dated in the future can't hide later ones; that clock must agree with the network's to within the window, as NTP keeps it. A scan takes at most 50 pages (1,000 messages): a bigger catch-up fails with `BacklogTooLargeError` rather than skip any. A failure ends the watch with its error. Nothing retries, not even the SDK's own retries, whose waits an abort can't cut short, so the caller decides how to resume. A WebSocket or Matrix `/sync` implementation can replace the poller without touching anything above `providers/`.
  - **Only the user's own messages** for now (`sender: 'me'`): the listener never reads anyone else's messages. Other senders join the query with the first watch that needs them.
- **New providers**: implement `Messenger` and `AccessRequester`, add a branch in `app.ts`. A provider maps its messages to `core/types.ts` itself. A message's `text` is plain, as its chat shows it: the provider turns its own markup into that, and keeps the markup as `html`. `Message.ownText` is a cautious reading of the words the sender wrote themselves that leaves out whatever may be someone else's: only the provider knows how its text marks a quote or a reply's copy of another message (Beeper: `providers/beeper/own-text.ts`, for Matrix's HTML and the plain text bridges write). It can drop some of the sender's own words too, so the MCP tools leave it out and give Claude the text itself.
- **Language model** (`core/model.ts`): `LanguageModel.write({ instructions, input })` is text in, text out, with no tools, so other people's words in its input can at worst change what it writes, never make it act. It landed with its first consumer, the digest. The implementation, `providers/claude-code/model.ts`, runs `claude -p` as installed and signed in on the host, so it runs on the owner's Claude subscription, never an API key (`--bare` would read only API keys). Each run gets the input on stdin, never on a command line; no tools (`--tools ""`); no hooks, plugins or CLAUDE.md, the owner's or a directory's above the run (`--safe-mode`); no MCP servers (`--strict-mcp-config` and `--safe-mode`, each enough alone; `--tools ""` leaves them in); none of the subscription's claude.ai connectors, such as Gmail (`ENABLE_CLAUDEAI_MCP_SERVERS=false`, `--strict-mcp-config` and `--safe-mode`); nothing attached to the input; no transcript (`--no-session-persistence` and `CLAUDE_CODE_SKIP_PROMPT_HISTORY`, each enough alone), memory or prompt history; an empty working directory of its own, removed afterwards; and an environment with only sign-in, network and locale variables, so no Beeper token, API key or variable of a calling session reaches it. Nothing attached matters because Claude Code reads a file an @-mention in a prompt names, tools or not, so a message saying `@~/claude-messenger/.env` would put the token in front of the model. Attachments are switched off (`CLAUDE_CODE_DISABLE_ATTACHMENTS`), and every "@" in the input reaches Claude Code as a full-width "＠", which mentions nothing; either alone stops the read. `test/claude-code-binary.integration.test.ts` proves each of these against the installed Claude Code, which CI installs at its latest, as hosts auto-update to it: each guard alone, with its twin taken out, and a control without both that shows the thing happen. The claude.ai connectors are the exception: Claude Code fetches them from claude.ai with the subscription sign-in, where no stand-in can answer, so that they stay out rests on Claude Code's code, where each of the three turns them off, and on its debug log, which says they are off. A sign-in the API turns away fails at once, with the API's reason; an API key turned away, or a rate limit, Claude Code retries for about three minutes first. A Claude Code too old for `--safe-mode` rejects the flag, so the run fails before the model sees anything. `createLanguageModel` in `app.ts` is where an automation gets it.
- **Daily digest** (`assistant/digest/`, `claude-messenger digest`): the first automation that writes. `ActivityCollector` reads, through the `GuardedMessenger`, the main inbox's chats active in the window (not archived or low priority), each only as far back as it needs, keeping each message's plain `text`, as the chat shows it; after paging through the chat list it reads the first page again, for a chat that moved to the top meanwhile. `renderBriefing` lays them out one line per message, the chats likely to need the owner first (a mention, or a direct chat waiting on them; muted chats last), others' words folded onto one line each with control and invisible characters dropped, so none can pose as the briefing's own lines, and every name but the owner's "You", and every reaction, in quotes, so none can pass for the owner. `DigestWriter` has the model write "Needs you" and "Everything else", and makes what it wrote safe to show (`safe-markdown.ts`): every link (a domain or IP address with a path or port among them), email address, phone number and code becomes "(link)", "(email address)" or "(number)", written fullwidth or split by invisible characters too, and what Markdown could still turn into a link or HTML is escaped, each in time linear in the text. A bare domain stays, as names hold them (Amazon.com). Beneath it goes a count of what it covers and every gap: chats it couldn't read, chats it read only in part, chats left out for length, more chats than it reads. With nothing new it says so without calling the model. `--since` sets where a digest starts, up to seven days back, so each morning can start where the last one did; a message dated before the window it reached Beeper in, as a bridge catching up can make, or a morning that failed, isn't covered by the next. Delivery is outside the code (`docs/STATUS.md`, Daily digest).
- **Credentials**: `AccessRequester` (`core/access.ts`) is how this app gets its provider credential. A Claude session drives installs and its transcript is readable, so the credential must never pass through a terminal, a chat or a screen: the owner approves in the provider's own window, and the credential travels from the provider straight into `.env` (`claude-messenger connect`). The Beeper implementation (`providers/beeper/access.ts`) drives Beeper Desktop's OAuth approval box (dynamic client registration + PKCE), waiting for sign-in first and re-asking when Beeper closes an unanswered box. It reports the terms the owner approved; whether the app keeps them is decided above every provider, by `GuardedAccessRequester` (`policy/access.ts`). The CLI sees only the port.
- **Automations** (`assistant/`): build on `GuardedMessenger` only, so every automated action inherits policy + audit for free. The first is the @Claude listener: `mentionsClaude` decides whether a message addresses Claude (the user's own message naming `@claude` as a word in its `ownText`, so not in a quote, a reply's copy of another message, a tapback's quote of one, or a pill naming someone in the chat; and not a reaction), and `watchMentions` follows the user's messages for those. What the text can't tell apart still counts: a message the user forwards, or one an app sends as them. It sees a message as it first arrives, so whatever acts on a mention reads it again first. Diagnostics get a deliberately narrow `ConnectivityProbe` (checkConnection only) — the unguarded provider is never handed out of the composition root.

## Security notes

- The Beeper token is all-powerful; treat it like a password. It lives in `.env` (gitignored, owner-only) or the process environment, is never logged or displayed, and can be revoked any time in Beeper (Settings → Integrations → Approved connections).
- `connect` asks for a read-only token unless told otherwise (`--allow-send`). Beeper's approval box lets the owner grant more than was asked; a token with write access nobody asked for, or with an expiry nothing renews, is revoked rather than saved (`GuardedAccessRequester`). Fail closed: an app that can't keep a credential's terms must not leave it working.
- Policy is enforced in this process, not by Beeper. Anyone with the raw token can bypass it — the layer protects against a confused/overreaching *agent*, not a malicious *human*.
- Defense in depth for reads Claude never needs: `read.chatDenylist` + account allowlists shrink the blast radius of prompt injection from message content (a message can't talk Claude into leaking a chat it cannot see).
- The digest's model reads other people's messages, so it has no tools and nothing it can be made to read: a message can at most change what the digest says. The digest goes to the owner as written, so a message can try to mislead the owner through it, as it could when read directly; the instructions tell the model never to repeat links, codes, phone numbers or email addresses, and any it writes anyway is replaced, so a digest can't hand the owner, or a session that carries it, somewhere to go. The model's input never touches disk, a command line or the audit log. The CLI prints the digest and keeps no copy. Whatever delivers it sees it: a Claude session that carries the digest to the owner holds it in that session's transcript, and reads it, and a message could try to steer that session through it. The session that runs it on the VPS has tools within reach of the token, so it never reads it as text: it gets the digest compressed and base64-encoded, and the project thread that posts it decodes it.
