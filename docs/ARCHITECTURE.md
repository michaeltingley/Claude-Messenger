# Architecture

## The constraint that shapes everything

Beeper is Matrix under the hood with end-to-end encryption: **only a device logged into your account can decrypt your messages**. Beeper therefore has no third-party cloud API. The official surface is the **Beeper Client API** — an HTTP + MCP server embedded in a logged-in Beeper client, historically Beeper Desktop (`localhost:23373`) and now also the official headless **Beeper Server** (same API, no GUI).

Consequence: Claude Messenger is a *client* of a Beeper endpoint that must run somewhere logged into your account. Where that endpoint runs is pure configuration (`BEEPER_BASE_URL`); nothing else changes.

> In practice the owner's account runs in **Beeper Desktop**, including on headless hosts (under Xvfb), and never in the headless **Beeper Server**: [beeper/cli#21](https://github.com/beeper/cli/issues/21) is open, and reports a Server install deleting a legacy account's bridge connections across every device. Server runs only the assistant's own, new account ([below](#the-assistants-own-account)). Because the endpoint is pure configuration, this choice touches nothing above `providers/` — which is the property this seam exists to provide.

## Layers

```
Claude (Claude Code / Desktop / claude.ai)
   │  MCP (stdio locally, or Streamable HTTP + bearer token when hosted)
┌──▼──────────────────────────────┐
│ mcp/    curated tools           │   deliberately narrow: no delete/archive
│ assistant/ automations          │   the daily digest (writes with the model);
│                                 │   @Claude mentions (own messages only)
├─────────────────────────────────┤
│ policy/ GuardedMessenger        │   PolicyEngine (pure decisions)
│         + JSONL audit log       │   read filters, send gates, rate limits
│         GuardedAccessRequester  │   keeps only credentials it can keep
├─────────────────────────────────┤
│ core/   Messenger port          │   provider-agnostic domain models
│         AccessRequester port    │   how the credential comes to exist
│         LanguageModel port      │   text in, text out: no tools
├─────────────────────────────────┤
│ providers/beeper/               │   @beeper/desktop-api adapter
│ providers/claude-code/          │   `claude -p` on the owner's subscription,
│                                 │   which talks to Anthropic, not Beeper
└──┬──────────────────────────────┘
   │  HTTPS + bearer token
Beeper Client API (Desktop app OR headless Beeper Server)
   │
Beeper cloud bridges ⇄ WhatsApp / Signal / Telegram / iMessage / ...
```

### Rules that keep it clean

1. **Nothing above `providers/` imports a provider SDK.** The `Messenger` interface (`core/messenger.ts`) is the seam. Tests run against `FakeMessenger`; a raw-Matrix provider (via Beeper's own `@beeper/pickle` / `@beeper/chat-adapter-matrix`) can be added without touching policy, MCP, or CLI.
2. **The tool layer only ever sees the `GuardedMessenger`.** Policy checks happen in-process *before* any provider call; denials throw `PolicyDeniedError` naming the rule. Read results are filtered so denylisted chats, and chats of accounts the allowlist leaves out, never enter Claude's context; a chat or message that comes with no account ID passes the account allowlist only when it is `'*'`. Likewise `connect` only gets the `GuardedAccessRequester`.
3. **`PolicyEngine` owns decisions, not I/O.** The clock and the rate-limit store (`RateWindow`) are injected: tests control time with a memory window, while the composition root wires a file-backed window so send limits survive process restarts (each CLI `send` is a fresh process).
4. **Audit content policy**: outbound text is recorded (you must be able to review what was said as you); read message content is never written to the audit log (your history doesn't belong in log files). The assistant's own account says nothing as you: it writes from what it read and sends only to you, who have every word of it in its chat, so its audit keeps each message's length instead (`recordSentText: false`). A watch records which message it handed on (chat and message IDs), never what it said. A failure is recorded by its code (`provider_error`, `not_found`, …), never its text: a provider's error text comes from outside, and can quote a message it read.

## Deployment topologies

| Topology | BEEPER_BASE_URL | Use case |
|---|---|---|
| Local | `http://localhost:23373` | Claude Code/Desktop on the same machine as Beeper Desktop |
| Tunnel | `https://<tunnel-host>` | Remote Claude (web sessions, automations) reaching your desktop via Tailscale/cloudflared |
| Assistant's own account | `http://127.0.0.1:23374` | The @Claude assistant's own Beeper account, on Beeper Server beside the owner's Beeper Desktop ([below](#the-assistants-own-account)) |
| Always-on desktop | `https://<tunnel-host>` | 24/7 GA fallback: Beeper Desktop + Remote Access on a machine that stays awake |

Beeper Desktop's *Remote Access* setting (Settings → Integrations → Advanced) binds the API to all interfaces and is designed for tunnels; auth stays bearer-token. Beeper ships no TLS — never expose the port raw.

## The assistant's own account

The @Claude assistant answers from a Beeper account of its own, in a private chat with the owner, so nothing it says is ever sent as the owner, and the owner's token stays read-only. That account needs a logged-in Beeper endpoint of its own. It runs on **Beeper Server**, not a second Beeper Desktop: Desktop's Client API is off until someone switches it on in its window, so a new account there can't be set up without a person at its screen, while Server's API answers from the start, sign-up included.

`deploy/assistant-beeper.sh` installs it as the system unit `assistant-beeper.service` on `127.0.0.1:23374`, and makes the assistant's own configuration directory, `~/.config/claude-messenger/assistant`, whose `.env` points there. Commands run from that directory act as the assistant. Nothing above `providers/` changes: only `BEEPER_BASE_URL` differs.

- **The owner's account never runs on Server.** [beeper/cli#21](https://github.com/beeper/cli/issues/21)'s data loss hit an existing account's bridges. Its maintainer traced the nightly build to the CLI, which installed Server's nightly channel whatever was asked (fixed on the CLI's main branch, but its latest release, 0.6.2, still does), and suspects a recovery-key reset, the one action that disconnects every cloud bridge, for the loss; the cause is unconfirmed. The assistant's account is new and has no bridges, and its build comes straight from Beeper's stable update feed, checked against the feed's SHA-512. The script refuses anything else the feed announces.
- **Signing it up.** `claude-messenger signup start`, then `signup finish`, run from that directory, create the account through Server's setup API and save its token straight into `.env`, so nobody sees it; only the emailed sign-up code, which works once, passes through whoever relays it. Finishing accepts Beeper's terms for the account, so it needs `--accept-terms`, checked before Beeper hears of the code. The port is `AccountSignup` (`core/signup.ts`); the Beeper side, `providers/beeper/signup.ts`, speaks plain HTTP, since the `@beeper/desktop-api` here (5.0.0) predates the setup API. It refuses an endpoint already signed in; signs straight back out of an account the address already had, which the code signs in to; and waits while Beeper sets the new account's encryption up, as Server 4.3.176 did by itself for the assistant's (passing through `needs-secrets`, which is therefore no sign of encryption set up elsewhere). Where Beeper leaves an account without any, it sets encryption up afresh, with a recovery key it neither shows nor keeps, only if the account never had any and has no chat networks, so never on the owner's. `signup encrypt` picks that up where it stopped. `test/signup.integration.test.ts` proves each, through the CLI, against the mock's model of the setup API.
- **Its chat with the owner.** The assistant answers in a direct chat between its account and the owner's. `claude-messenger start-chat --with <owner's user ID>`, run from its directory, opens it: Beeper reuses the direct chat there is, or makes a new one the owner is invited to, and the command prints its ID. `Messenger.startDirectChat` is a mutation like a send, since a new chat reaches the other person: the policy denies it unless `capabilities.startChat` is on and `startChat.userAllowlist` names that person (never `'*'`), on an account it may read; the audit records who it was with before Beeper is asked, and the chat after. The owner's own policy never allows it. Sending in that chat then takes `send.chatAllowlist`, as anywhere.
- **Answering.** `claude-messenger respond --assistant <its directory>`, run where the owner's own configuration is, answers the owner from that account (`assistant/responder/`). It holds two `GuardedMessenger`s, each under its own account's policy and audit: the owner's, read-only, which follows the owner's own messages (`watchMessages`) and reads; and the assistant's, which sends, in its chat with the owner alone. `findConversation` finds that chat as it starts, from both sides: the assistant's one account, not the owner's, and its one direct chat with one of the owner's users, which the owner's Beeper shows too (else: accept the invite). A request is an @Claude in any of the owner's chats (`mentionsClaude`), or anything the owner writes in that chat. For each, it reads the message again (`Messenger.getMessage`, guarded as `getChat` is: it may have been edited or deleted, and then asks nothing), its chat, and up to 30 of the chat's latest messages before it, from at most three pages; lays them out as the digest does (`assistant/text/lines.ts`, the owner as "The owner" and the assistant as "You", without quotes); and has the model answer, under the digest's guards (Language model, below). The answer is made safe to show (`safeMarkdown`), cut at a word to the policy's `send.maxCharsPerMessage`, and headed with the request's chat and time when it was asked elsewhere. A request that can't be answered (gone, refused by Beeper or a policy, or no answer from the model) gets a line in fixed words saying so, with its time, and the run goes on; any other failure ends the run. Each request is handled at most once: its checkpoint, `responder.json` in the assistant's state directory (IDs and times only, readable by the owner alone), records it before the answer is sent, so a crash in between loses the answer rather than send it twice. A restart resumes 15 minutes behind the latest of the owner's messages, more than Beeper's poller waits for a late one, but no more than six hours back; the first run starts from now. Its journal (stdout) gives what it did by IDs and kinds of failure; a failure that ends the run is given with its text only when that text is this app's own or the system's, since a provider's or the model's can quote a message.
- **It can't reach the owner.** It runs as a user of its own (`DynamicUser=`), sees no home directory and none of the owner's processes, and keeps the account's keys where only it can read them. Where systemd was built with BPF, as Ubuntu 26.04's is, it may also listen on its own port and on no other (never Desktop's 23373); a systemd built without it, like 24.04's, ignores that part, and `deploy/assistant-beeper.sh` warns of it. `test/assistant-beeper-sandbox.integration.test.ts` proves each under the real systemd, the port held on one and not on the other; that the real server runs under it, only a host can.
- **Its code is unpacked when it is installed.** Beeper Server is one executable whose launcher, on its first start, unpacks the rest of the server with `tar` into `$XDG_CACHE_HOME/BeeperServer/<build>`, and from then on runs what it finds there marked complete. Under the sandbox `tar` can't run: Ubuntu 26.04's opens files with `openat2()`, which the `RestrictSUIDSGID` that `DynamicUser=` implies refuses, and it does not fall back. So `deploy/assistant-beeper.sh` unpacks it as it installs the server, exactly as the launcher would, into `/opt/beeper-server/payload`, which the runtime can read but not change, and the unit points the launcher there. It first checks the launcher's own lines that say where it looks and that it runs what it finds, and finds the payload where a Node single executable keeps an asset; a build packaged any other way is refused before anything changes, so the running one stays. The tests' stand-in (`test/beeper-feed.ts`) is packaged the same way, and its launcher unpacks with `tar` as Beeper's does, so on Ubuntu 26.04 the sandbox test fails as the host did whenever the install leaves the unpacking to it.

## Extension points (deliberate, not speculative)

- **Streaming/triggers**: `Messenger.watchMessages` delivers messages as they reach the backend, each once, after a `since` time. It landed with its first consumer (the @Claude listener, `assistant/mentions.ts` and `claude-messenger mentions`), its Beeper implementation and its guarded wrapper in one change, as planned:
  - **Guarded**: `GuardedMessenger.watchMessages` checks the read policy before the provider is asked, hands on only the user's own messages whatever the provider returns, filters every message through the same visibility predicate as reads, and audits like a mutation: intent first (mandatory), a delivery entry before each message is handed on (mandatory; IDs only), the outcome last (best-effort). Idle polls write nothing.
  - **Beeper**: the Client API's WebSocket (`/v1/ws`, `message.upserted`) is experimental, so the provider polls message search instead (`providers/watch-by-polling.ts`, every `BEEPER_POLL_INTERVAL_MS`, default 5 s). Each scan re-reads a 10-minute window behind the previous one, because a message can reach Beeper after its own timestamp (a bridge reconnecting); one that arrives later than that is missed. The window follows the host clock, not message timestamps, so a message dated in the future can't hide later ones; that clock must agree with the network's to within the window, as NTP keeps it. A scan takes at most 50 pages (1,000 messages): a bigger catch-up fails with `BacklogTooLargeError` rather than skip any. A failure ends the watch with its error. Nothing retries, not even the SDK's own retries, whose waits an abort can't cut short, so the caller decides how to resume. A WebSocket or Matrix `/sync` implementation can replace the poller without touching anything above `providers/`.
  - **Only the user's own messages** for now (`sender: 'me'`): the listener never reads anyone else's messages. Other senders join the query with the first watch that needs them.
- **New providers**: implement `Messenger` and `AccessRequester` (and `AccountSignup`, to run the assistant's own account), add a branch in `app.ts`. A provider maps its messages to `core/types.ts` itself. A message's `text` is plain, as its chat shows it: the provider turns its own markup into that and leaves out the copy of the message a reply answers; when that leaves something out, `html` keeps the message as the provider gave it. `Message.ownText` is a cautious reading of the words the sender wrote themselves that leaves out whatever may be someone else's: only the provider knows how its text marks a quote or a reply's copy of another message (Beeper: `providers/beeper/own-text.ts`, for Matrix's HTML and the plain text bridges write). It can drop some of the sender's own words too, so the MCP tools leave it out and give Claude the text itself. Beeper's two readings take markup from one table of what each element a message's HTML may hold shows as in the chat (`providers/beeper/elements.ts`), so a word partly in bold is one word in both.
- **Language model** (`core/model.ts`): `LanguageModel.write({ instructions, input })` is text in, text out, with no tools, so other people's words in its input can at worst change what it writes, never make it act. It landed with its first consumer, the digest. The implementation, `providers/claude-code/model.ts`, runs `claude -p` as installed and signed in on the host, so it runs on the owner's Claude subscription, never an API key (`--bare` would read only API keys). Each run gets the input on stdin, never on a command line; no tools (`--tools ""`); no hooks, plugins or CLAUDE.md, the owner's or a directory's above the run (`--safe-mode`); no MCP servers (`--strict-mcp-config` and `--safe-mode`, each enough alone; `--tools ""` leaves them in); none of the subscription's claude.ai connectors, such as Gmail (`ENABLE_CLAUDEAI_MCP_SERVERS=false`, `--strict-mcp-config` and `--safe-mode`); nothing attached to the input; no transcript (`--no-session-persistence` and `CLAUDE_CODE_SKIP_PROMPT_HISTORY`, each enough alone), memory or prompt history; an empty working directory of its own, removed afterwards; and an environment with only sign-in, network and locale variables, so no Beeper token, API key or variable of a calling session reaches it. Nothing attached matters because Claude Code reads a file an @-mention in a prompt names, tools or not, so a message saying `@~/claude-messenger/.env` would put the token in front of the model. Attachments are switched off (`CLAUDE_CODE_DISABLE_ATTACHMENTS`), and every "@" in the input reaches Claude Code as a full-width "＠", which mentions nothing; either alone stops the read. `test/claude-code-binary.integration.test.ts` proves each of these against the installed Claude Code, which CI installs at its latest, as hosts auto-update to it: each guard alone, with its twin taken out, and a control without both that shows the thing happen. The claude.ai connectors are the exception: Claude Code fetches them from claude.ai with the subscription sign-in, where no stand-in can answer, so that they stay out rests on Claude Code's code, where each of the three turns them off, and on its debug log, which says they are off. A sign-in the API turns away fails at once, with the API's reason; an API key turned away, or a rate limit, Claude Code retries for about three minutes first. A Claude Code too old for `--safe-mode` rejects the flag, so the run fails before the model sees anything. `createLanguageModel` in `app.ts` is where an automation gets it.
- **Daily digest** (`assistant/digest/`, `claude-messenger digest`): the first automation that writes. How it lays messages out for the model and makes what the model wrote safe to show are kept in `assistant/text/`, apart from the digest, for any automation that writes from messages. `ActivityCollector` reads, through the `GuardedMessenger`, the main inbox's chats active in the window (not archived or low priority), each only as far back as it needs, keeping each message's plain `text`, as the chat shows it; after paging through the chat list it reads the first page again, for a chat that moved to the top meanwhile, and ranks it, like the rest, by what it had in the window. `renderBriefing` lays them out one line per message (`assistant/text/lines.ts`), the chats likely to need the owner first (a mention, or a direct chat waiting on them; muted chats last), others' words folded onto one line each with control and invisible characters dropped, so none can pose as the briefing's own lines; every chat's name, every name but the owner's "You", and every reaction in quotes, with every mark that reads as a double quote taken out of them, so none can pass for the owner; and each message's text last on its line, after the first colon outside quotes that follows its sender, so it can't pass for anything the line says of it. `DigestWriter` has the model write "Needs you" and "Everything else", and makes what it wrote safe to show (`assistant/text/safe-markdown.ts`): every link, web address (Amazon.com among them) and IPv4 address becomes "(link)", every email address "(email address)", every number of six digits or more that isn't a date, time or amount (a phone, account or card number, a code) "(number)", its digits grouped by spaces, line breaks inside a paragraph or up to three signs at a time (`numbers.ts`), and every long code of letters and digits, Matrix recovery key, or code written in groups of one length, as a product key or a gift card's is (three or more joined by dashes, four or more by spaces), "(code)", written fullwidth, in lookalike symbols or split by invisible characters too; a file's name stays when its type ends no web address (notes.txt, but not report.md). What Markdown could still turn into a link, HTML or code, or emphasis that would split an address, is escaped, each in time linear in the text. Some gets through: a number spelled out or written in letters that look like digits, a short code of letters and digits (A1B2C3), a code in groups that holds no digit, has a group that reads as a word, or has fewer groups than that, digits split by a comma or a semicolon and a space, as a list's are, or by more than three signs at a time, and an IPv6 address. Beneath it goes a count of what it covers and every gap: chats it couldn't read, chats it read only in part, chats left out for length, more chats than it reads. With nothing new it says so without calling the model. `--since` sets where a digest starts, up to seven days back, so each morning can start where the last one did; a message dated before the window it reached Beeper in, as a bridge catching up can make, or a morning that failed, isn't covered by the next. Delivery is outside the code (`docs/STATUS.md`, Daily digest).
- **Credentials**: `AccessRequester` (`core/access.ts`) is how this app gets its provider credential. A Claude session drives installs and its transcript is readable, so the credential must never pass through a terminal, a chat or a screen: the owner approves in the provider's own window, and the credential travels from the provider straight into `.env` (`claude-messenger connect`). The Beeper implementation (`providers/beeper/access.ts`) drives Beeper Desktop's OAuth approval box (dynamic client registration + PKCE), waiting for sign-in first and re-asking when Beeper closes an unanswered box. It reports the terms the owner approved; whether the app keeps them is decided above every provider, by `GuardedAccessRequester` (`policy/access.ts`). The CLI sees only the port.
- **Automations** (`assistant/`): build on `GuardedMessenger` only, so every automated action inherits policy + audit for free. The first is the @Claude listener: `mentionsClaude` decides whether a message addresses Claude (the user's own message naming `@claude` as a word in its `ownText`, so not in a quote, a reply's copy of another message, a tapback's quote of one, or a pill naming someone in the chat; and not a reaction), and `watchMentions` follows the user's messages for those. What the text can't tell apart still counts: a message the user forwards, or one an app sends as them. It sees a message as it first arrives, so whatever acts on a mention reads it again first, as the responder that answers it does (Answering, above). Diagnostics get a deliberately narrow `ConnectivityProbe` (checkConnection only) — the unguarded provider is never handed out of the composition root.

## Security notes

- The Beeper token is all-powerful; treat it like a password. It lives in `.env` (gitignored, owner-only) or the process environment, is never logged or displayed, and can be revoked any time in Beeper (Settings → Integrations → Approved connections).
- `connect` asks for a read-only token unless told otherwise (`--allow-send`). Beeper's approval box lets the owner grant more than was asked; a token with write access nobody asked for, or with an expiry nothing renews, is revoked rather than saved (`GuardedAccessRequester`). Fail closed: an app that can't keep a credential's terms must not leave it working.
- Policy is enforced in this process, not by Beeper. Anyone with the raw token can bypass it — the layer protects against a confused/overreaching *agent*, not a malicious *human*.
- Defense in depth for reads Claude never needs: `read.chatDenylist` + account allowlists shrink the blast radius of prompt injection from message content (a message can't talk Claude into leaking a chat it cannot see).
- The responder's model reads what the digest's does, a request's chat at a time, under the same guards, and what it writes passes the same filter. Its answers go only to the owner, in the assistant's chat, the one chat the assistant's policy lets it send to: a message in a chat the owner asks about can try to steer an answer, as it can a digest, but not make it act, reach anyone else, or carry a link, a code or a number the filter knows. Its input never touches disk, a command line, its journal or either audit log.
- The digest's model reads other people's messages, so it has no tools and nothing it can be made to read: a message can at most change what the digest says. The digest goes to the owner as written, so a message can try to mislead the owner through it, as it could when read directly; the instructions tell the model never to repeat links, web addresses, codes, email addresses, or phone, account or card numbers, and what it writes anyway is replaced, so a digest can't hand the owner, or a session that carries it, somewhere to go in a form a linkifier or a dialer reads, but for the few forms the filter can't tell from words (Daily digest, above). The model's input never touches disk, a command line or the audit log. The CLI prints the digest and keeps no copy. Whatever delivers it sees it: a Claude session that carries the digest to the owner holds it in that session's transcript, and reads it, and a message could try to steer that session through it. The session that runs it on the VPS has tools within reach of the token, so it never reads it as text: it gets the digest compressed and base64-encoded, and the project thread that posts it decodes it.
